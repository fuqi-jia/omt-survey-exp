# 2026-10-09 暂存完整性故障与恢复

本目录保存已执行的人工恢复脚本与证据，不是需要再次运行的启动流程。

13:32 UTC 起，整数伴随实验出现 7 个作业无效。两种求解器的工作进程均在读取输入时抛出 `FileNotFoundError`，尚未开始求解。Panda3、Panda6 的文件清单检查发现部分整数文件缺失或仅有部分字节，但 `.eos-stage.json` 已存在，其时间与控制端标记一致。平台的 rsync 会复制此标记，`stage_path` 又仅凭标记中的源指纹跳过传输；因此先复制到的标记会使后续暂存检查误判为完整。

恢复仅涉及本项目的数据和实验：

1. 将该实验标为暂不派发，已有任务继续运行。第一次标记遇到正在执行的派发批次，状态被批次收尾覆盖，随后再次设置并核对；未停止共享调度服务。
2. 将控制端本项目的暂存标记移入本目录保存，避免后续传输提前复制完整性声明。输入文件、清单、冻结规格和求解程序没有改变。
3. 对 Panda3、Panda6 强制增量同步本项目的数据目录，并分别验证全部 508 个 BV/整数文件的大小与 SHA256。完整核验记录见两份 `*-full-hash-repair.json`。
4. 为 7 个失败作业保存数据库行、两份错误日志及完整原始作业归档；逐文件验证归档哈希、输入身份与冻结运行程序哈希。原工作目录另外改名保留，防止重试覆盖。
5. 调用 ExperimentOS 的 `Store.release_to_pending`，将同一批 run ID 按基础设施失败重新排队，并使用官方 `eos resume` 恢复实验。未新增或删减输入，也没有挑选更好的性能结果。原始尝试没有启动求解器，正式观测采用修复后同一预算的配对运行。

7 个原始压缩归档位于 `runs/full20261009/raw/staging-incident/`，不进入 Git；其路径、完整哈希和逐次恢复信息记录在本目录。`requeue-complete.json` 记录恢复时间与 run ID，后续仍须等待重试完成并通过完整覆盖审计。

另修正了进度统计：ExperimentOS 重新排队时暂留旧 `metrics_json`，统计程序现在只读终态作业的指标，避免将旧失败记录误作正在重试任务的新结果。原始失败证据仍完整保存。
